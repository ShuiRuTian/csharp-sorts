# Task 16 Agent B — C# Performance Idioms Review

## Verdict: FINDINGS

## Findings

1. **Critical — GlideMerge.cs:169-210 (`MergeOneAtBegin`/`MergeOneAtEnd`): upstream's explicitly-branchless merge step ported as `if/else` branches.**
   Upstream (upstream/glidesort/src/branchless_merge.rs:176-196, 229-245) is branchless by design: `select(right_less, right_scan, left_scan)` pointer select, `copy_nonoverlapping`, and cursor advance via integer arithmetic (`left_begin += right_less as usize` style — the "do not touch unless benchmarking" comment). The port instead does `if (rightLess) { write right; _rightBegin++; } else { write left; _leftBegin++; }` — two data-dependent branches per merged element (store selection + cursor increment). These two methods are the innermost step of *every* GlideSort merge: `FinishMerge`/`FinishMergeAtBegin/End/Interleaved` and the small-sort networks (`FinalMergeFromDstInto`, `DoubleMergeFromSrcToDst`) all call them once per element, so on random data essentially every element GlideSort moves outside quicksort passes through here, with ~50% mispredicts (Arm64 ≈ 10-15 cycles each). DriftMerge.cs:108-145 (`MergeUp`/`MergeDown`) ports the same upstream shape correctly with conditional-ref + ternary arithmetic — the idiom was in-repo. Plausibly a large fraction of GlideSort's 2.6x random-int gap. Fix: `ref T src = ref rightLess ? ref Unsafe.Add(ref r, _rightBegin) : ref Unsafe.Add(ref l, _leftBegin); Unsafe.Add(ref d, _dstBegin) = src; _dstBegin++; int rl = rightLess ? 1 : 0; _rightBegin += rl; _leftBegin += 1 - rl;`

2. **Critical — GlideQuicksort.cs:431-480, 597-691 (`PartitionOneForward`/`Backward` + Inverted variants): branchy store-select, dropped upstream branchless double-store, and per-element `Span.Slice` machinery in the partition inner loop.**
   Upstream `partition_one_forward/backward` (stable_quicksort.rs:157-219) per element: compare, branchless pointer `select`, then for `size_of::<T>() <= size_of::<usize>()` an unconditional **double-store** to both `dest_out` and `scratch_out` (the comment-annotated trick that eliminates even the store-address cmov), else copy to the selected pointer; counters advance via `+= as usize`; scan shrinks by one pointer add (`add_begin(1)`). The port per element: (a) data-dependent `if (lessThanPivot)` branch selecting the store (unpredictable, ~50% mispredict) plus a second `if (lessThanPivot) _numAtDestBegin++` branch; (b) double-store optimization silently dropped; (c) `ForwardScan.SplitOffBegin(1)` → `TwoPieceSpan.SplitAt` → two `Span.Slice` calls (each with bounds validation) plus struct field copies vs one pointer bump; (d) scan read and stores go through `TwoPieceSpan` indexers = extra branch + span bounds check each. `PartitionOneAny` (597-638) additionally computes `ForwardScan.Length + BackwardScan.Length` and does `_pivotRel` bookkeeping per element, where upstream tracks the pivot only at scan boundaries. This is the loop that processes all random input during the quicksort phase. Fix: restructure to base-ref + int-cursor exactly like DriftQuicksort.cs:306-356 (`PartitionState` + `PartitionOne`), which ports the same algorithm family with correct .NET idioms (branchless ternary arithmetic, `Unsafe.Add`, zero per-element slicing); optionally port the ≤-pointer-size double-store.

3. **Important — GlideSmallSort.cs:134-149, 381-398: nested ArrayPool round-trips per small-sort on the reference-T path — beyond the documented "one ArrayPool path".**
   For `IsReferenceOrContainsReferences<T>()`, `BlockInsertionSort` rents 32 and, *inside* that region, `PartialSortInto` rents/returns 64 per chunk (2-3 chunks per ≤48-element region): ~3-4 pool ops plus `clearArray:true` clears (32+64+64 slots) per small-sort call, invoked O(n/48) times per sort (every quicksort base case and eager run) for reference/managed-containing T. Value types (int/double, the benchmark matrix) use stackalloc and are unaffected. Fix: single `Rent(64)` in `BlockInsertionSort` passed down as scratch (64 covers both the insertion scratch ≤32 and the network's 64), or a ThreadStatic buffer like QuadSort/DriftSort's scratch caches.

4. **Minor — QuadsortImpl.cs:831, 837-838, 841-843 (`PartialForwardMerge`) and 928-995 (`PartialBackwardMerge`): `if (le) ptl++; else ptr++;` where the clang-compiled C ternary (`cmp(ptl,ptr) <= 0 ? *ptl++ : *ptr++`) is branchless pointer-select + increment.** The same file already uses the branchless idiom (`ptl += le ? 1 : 0; ptr += le ? 0 : 1`) in `CrossMerge`/`ParityMerge` — inconsistent. Bounded blast radius: partial merges run only on the sub-block tail per merge pass, not the main volume. Fix: ternary increments to match the rest of the file.

5. **Minor — span-indexer residuals in linear scans where the file idiom is ref-cursor:** DriftImpl.cs:198-212 (`FindExistingRun` — while-loop with `v[runLen]` inside the condition, a non-canonical loop shape the JIT's bounds-check elimination handles unreliably; this scan is the whole cost on the flagship sorted-input path), GlideMerge.cs:49-50 (`ShrinkStableMerge` descending `right[i]` loop), GlidesortImpl.cs:190-207 (`RunLengthAtStart` — canonical ascending for-loop, likely BCE'd; listed for completeness). Impact: ≤1 bounds check per element on one linear pass. Fix: `MemoryMarshal.GetReference` + `Unsafe.Add` cursors. GlideQuicksort.cs:305-310 (`CopyTwoPieceToTwoPiece`) is the same class of cost for base-case region moves (O(n) per sort, per-element ~6 extra instructions vs memmove) — could special-case adjacent pieces into `Span.CopyTo`.

6. **Minor — Comparers.cs:24, 31: `InterfaceCmp<T>.IsLess` / `ComparisonCmp<T>.IsLess` lack `[MethodImpl(AggressiveInlining)]`** while sibling adapters (`ComparableCmp`, `ComparerAdapter`) have it. Default JIT heuristics likely inline these tiny wrappers anyway, and the virtual/delegate call dominates — cosmetic consistency fix only.

## Checked-but-clean

- Devirtualization: zero raw `.CompareTo`/`IComparer` calls inside kernels (grep over src/Sorts hits only the designed Comparers.cs adapters); every hot-loop comparison flows through `TC : struct, IIsLess<T>`.
- `ComparableCmp<T>`/`ComparerAdapter` carry AggressiveInlining; `InterfaceCmp` uses cached `Comparer<T>.Default` — no per-call creation, no double-wrapping anywhere.
- `SmallSortConfig<T>.IsFreezeLike` (DriftSmallSort.cs:311-317) is a `static readonly` field in a per-T static class — `typeof(T).IsValueType` computed once; `Threshold<T>()` reads the cached field.
- `RuntimeHelpers.IsReferenceOrContainsReferences<T>()` (GlideSmallSort.cs:134/381) is a JIT intrinsic — constant-folded, no per-call reflection.
- Scratch policies match the documented ones exactly (QuadSort swap_size + 4MiB `8L` cap + OOM 512 fallback + ThreadStatic 64; GlideSort n/1MiB/1GiB/8th formula; DriftSort allocLen + ThreadStatic 512 + stackalloc run stacks); no other hidden allocations — no LINQ, closures, delegate creation, or boxing found in steady-state paths.
- NoInlining placement faithful to upstream `#[inline(never)]`: DriftQuicksort.StableQuicksort, DriftSmallSort.SortSmallGeneral, GlideSmallSort.DoubleMergeFromSrcToDst, GlideMerge.FinishMerge×4; all throw helpers are NoInlining/cold; no backwards cases (no micro-op carries NoInlining).
- QuadSort micro-ops (BranchlessSwap, Head/TailBranchlessMerge, SwapPairIf, GtAt, LeAt) all AggressiveInlining with cmov-shaped ternaries throughout; DriftSort kernels (DriftMerge.MergeUp/Down, DriftSmallSort.SmallMergeUp/Down + Sort4Stable conditional-refs, DriftQuicksort.PartitionOne) are correctly branchless — the model implementations for findings 1-2.
- Scratch-size arithmetic overflow-safe: Powersort ulong math; GlidesortAllocSize and DriftSort allocLen int math bounded; EagerSort width-doubling guarded; RotateMerge `2L` guards intact; the only int-exposure deferral remains the known QuadMerge/TailMerge `pta+block` item — no new ones.
- Known-minor items verified unchanged and not re-flagged: MergeStack class, GlideSort +1,136B/call, DriftSmallSort MinSmallSortScratchLen 50-vs-49, ThreadStatic 512 sizing, runtime `invert` bool in drift quicksort (GlideQuicksort's analogous runtime invert/forward dispatch is loop-invariant and predictable — not a hazard).
